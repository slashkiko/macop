macop / personal source install

個人署名インストールガイド

人間が判断するのは、使用するApple Development証明書だけです。source取得、profile更新、 ビルド、署名、検証、置換はpersonal-install.shが実行します。

人間が選択・承認 シェルが自動実行 自動検証・安全停止
信頼境界: updaterはGitHub上のslashkiko/macopのmainを信頼します。 commit署名やActions結果を利用者側では再確認せず、make ciも再実行しません。 GitHubまたは管理者アカウントが侵害された場合、悪意あるsourceも利用者自身の証明書で署名され得ます。

全体像

01 / HUMAN

証明書を選ぶ

初回と証明書更新時だけ、一覧から使用するApple Development証明書を選びます。

02 / SOURCE

公式mainをfresh clone

更新ごとに一時directoryへ公式mainをcloneし、元のcheckoutは変更しません。

03 / INSTALL

署名を検証して置換

profile、Team ID、entitlement、broker generationを確認し、失敗時は旧版を残します。

GitHub: slashkiko/macop main ──fresh clone──▶ 一時source
                                                  │
人間: Apple Development証明書を選択 ──保存──▶ profile作成
                                                  │
                                                  ▼
                                   build → 署名 → 検証 → atomic install

初回セットアップ

  1. 人間 / Xcode

    1. Apple Development証明書を用意する

    XcodeのSettings → AccountsへApple IDを追加し、使用するteamで証明書を作成します。 これはApple側で必要な初回操作で、秘密鍵はmacOS Keychainに保持されます。

  2. 人間 / Terminal

    2. setupを起動し、証明書を番号で選ぶ

    git clone https://github.com/slashkiko/macop.git
cd macop
scripts/personal-install.sh setup

    表示された一覧から証明書を1つ選びます。SHA-1のコピーやPATH optionの指定は不要です。

  3. シェル

    3. profile生成からインストールまで実行する

    • 選択した証明書を40文字SHA-1へ固定
    • Xcode automatic signingでdevelopment profileを作成または更新
    • profileのTeam ID、bundle ID、Keychain access groups、有効期限を検証
    • 全componentをrelease buildし、同じ証明書で署名
    • 署名、hardened runtime、broker generationをread-back
    • PATHを設定し、transactional installerで公開
  4. 自動検証

    4. 成功後だけfingerprintを保存する

    ~/Library/Application Support/macop/personal-signing-identityへSHA-1だけをmode 0600で保存します。秘密鍵、Apple ID、Team IDは保存しません。

通常の更新

  1. 人間 / Terminal

    1. 更新コマンドを1回実行する

    scripts/personal-install.sh update

    証明書、branch、revisionを選び直す必要はありません。

  2. シェル / Git

    2. 保存状態を確認し、公式mainをfresh cloneする

    保存済みSHA-1と保存fileのowner・mode・link数を確認した後、公式URLのmainだけを 一時directoryへcloneします。現在のcheckoutのbranch、差分、履歴は変更しません。

  3. シェル / Xcode

    3. cloneしたsourceを署名して更新する

    GitHub側のCIを品質ゲートとして信頼するため、利用者側のmake ciは省略します。 一時clone内のscriptがprofile更新、build、署名、preflight、置換を実行します。

  4. 自動検証

    4. 完全なgenerationだけを採用し、一時cloneを消す

    検証に失敗すれば旧generationを維持またはrollbackします。成否にかかわらず一時cloneは削除します。

証明書が更新・失効した場合

新しい証明書へ暗黙には切り替えません。setupを再実行し、一覧から新しい証明書を選びます。

scripts/personal-install.sh setup --replace-identity

非対話でfingerprintを指定する場合は、rotation flagも同時に渡します。

scripts/personal-install.sh setup \
  --signing-identity NEW_40_CHARACTER_SHA1 \
  --replace-identity

既存インストールと新しい署名のTeam IDが違えばinstallerが拒否します。保存済みSHA-1は、 新しい署名でのインストールが成功した後にだけ置換されます。

担当者ごとの責任

人間側

  • XcodeへApple IDを登録して証明書を用意する
  • 初回とrotation時に、使用する証明書を選ぶ
  • update commandを起動する
  • macOSが表示するKeychain・Xcodeのsystem promptを承認する

このうち、macop固有の判断は証明書の選択だけです。

GitHubとシェル側

  • GitHub: mainを配信し、repositoryのCIを実行する
  • シェル: 公式mainのfresh cloneと一時directoryの後始末
  • シェル: fingerprint、profile、Team ID、entitlementの検証
  • シェル: release build、同一署名、broker probe
  • シェル: atomicなgeneration置換と失敗時のrollback

残す検証と、その理由

確認内容 必要性 残す理由
保存fileが通常file、本人所有、mode 0600、hard link 1 防御的 symlinkや共有可能なfileを状態として使わず、証明書fingerprintの意図しない差し替えを検出するため。
保存したSHA-1とKeychain上のApple Development証明書が一致 必須 同名の別証明書やad-hoc署名へ暗黙に切り替わると、更新後にbrokerとKeychain accessが壊れるため。
profileのTeam ID、bundle ID、Keychain groups、有効期限 必須 署名できても、profileが別team・別app・期限切れなら必要なKeychain capabilityを利用できないため。
全componentの署名、Team ID、entitlement、hardened runtime 必須 CLI、agent、appが異なる署名世代になると相互認証に失敗し、broker境界を維持できないため。
manifest、broker preflight、transactional置換 必須 build成功だけでは実際に起動・接続できるとは限らず、途中失敗で新旧componentが混在するのを防ぐため。
clone先の期待fileと一時directoryの後始末 防御的 root-ownedでstickyな/private/tmp配下へ固定し、不完全なcloneを早く検出して途中物を残し続けないため。
省いた確認: commit署名、利用者側でのActions status確認、make ciは更新scriptでは行いません。 これらはsourceの信頼判断であり、上の検証は「取得したsourceを、このMacで壊れない一世代として署名・置換できるか」を確認します。

失敗したとき

状況 自動処理 既存インストール
公式mainをcloneできない build前に停止し、一時directoryを削除 変更しない
証明書がKeychainにない／失効 profile生成前に停止 変更しない
profileを発行・更新できない 署名・publicationへ進まず停止 変更しない
Team IDやentitlementが一致しない 検証で拒否 変更しない
置換中にbuild・probe・filesystem操作が失敗 transaction journalからrollback 旧generationへ戻す
証明書rotationに失敗 新fingerprintを保存しない 旧署名のまま維持

この方式が確認するもの／しないもの

  • 確認する: clone成功、保存状態、Apple証明書、profile、Team ID、entitlement、component整合性。
  • 確認しない: 利用者側のcommit署名、GitHub Actionsの成功status、ローカルmake ci。
  • Appleコード署名はbinaryと署名者を結び付けますが、sourceが善意であることは保証しません。
  • GitHubまたは管理者の認証情報まで侵害された場合、この方式だけでは正規更新と区別できません。
  • Personal Teamのprofileには有効期限があり、更新時にXcode accountやnetwork接続が必要になる場合があります。
  • 生成物は自分の署名環境向けであり、他人へ配布する正式リリースbinaryではありません。
